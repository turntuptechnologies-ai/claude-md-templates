## コミットメッセージ規約

[Conventional Commits](https://www.conventionalcommits.org/) に従う。

```
<type>: <description> (#<issue-number>)
```

### type 一覧

| type | 用途 |
|------|------|
| `feat` | 新機能の追加 |
| `fix` | バグ修正 |
| `docs` | ドキュメントのみの変更 |
| `test` | テストの追加・修正 |
| `refactor` | リファクタリング（機能変更なし） |
| `chore` | ビルド・CI・依存関係等の雑務 |
| `perf` | パフォーマンス改善 |

### ルール

- description は{{ 日本語 / English }}で記述する
- Issue 番号がある場合は末尾に `(#番号)` を付ける
- squash merge 時の PR タイトルもこの規約に従う

## 開発フロー

1. **Issue 作成** — コード・ドキュメント等の変更には必ず Issue を作成し、調査内容・判断の経緯をコメントに記録する
   - `backlog` ラベル: 優先度が低く、通常の開発サイクルでは取り組まない Issue に付与する。「オープンの Issue に取り組んで」等の指示では対象外とする
2. **ブランチ作成** — Issue に紐づくブランチで作業する。命名規則: `issue-<番号>/<簡単な説明>`（例: `issue-42/add-user-auth`）
3. **実装** — 作業中は適宜 commit・push を行う。**main への直接 push は禁止**
4. **PR 作成** — Issue を参照する（`Closes #42` 等）
5. **コードレビュー** — マージ前にレビューする。セキュリティ観点のチェックを含める（認証・認可の抜け漏れ、入力バリデーション、インジェクション対策等）
6. **マージ** — squash merge を使用し、マージ後にブランチを削除する
